# 基于3D高斯点云的实时渲染方法研究与实现

## 摘要

随着数字内容生产、虚拟现实和三维交互系统的发展，兼顾真实感与实时性的场景表示方法成为计算机图形学的重要研究方向。传统多边形网格渲染方案在工业界应用成熟，但在复杂真实场景重建中存在建模成本高、细节恢复困难等问题；以 NeRF 为代表的神经隐式表示方法虽然能够获得较高的新视角合成质量，却普遍依赖高代价的体积分推理过程，难以直接满足实时引擎场景中的交互需求。3D Gaussian Splatting 通过显式高斯分布对场景进行建模，在渲染质量和实时性能之间提供了新的折中路径。围绕这一背景，本文以 Unity 引擎为平台，研究并实现了一套面向实时渲染的 3D 高斯点云渲染方案。

本文首先分析 3D 高斯点云的数据组织方式与屏幕空间泼溅渲染原理，梳理高斯中心、缩放、旋转、透明度以及球谐颜色系数在渲染流程中的作用。随后，结合 Unity 工程环境，设计了由数据读取、参数重排、GPU 缓冲管理、相机相关深度排序、屏幕空间高斯绘制以及运行时辅助工具组成的整体系统架构。其中，在数据阶段实现了针对二进制 PLY 文件的结构化解析，并依据渲染阶段的数据访问需求对球谐系数进行离线重排；在渲染阶段使用 Compute Shader 完成基于相机视角的深度键计算，结合 GPU bitonic merge sort 完成高斯实例排序，再由自定义 Shader 在屏幕空间近似二维高斯核并执行透明混合；在工具阶段实现了相机姿态重建、性能基准测试以及图像质量对比功能，为方法验证与工程迭代提供支撑。

从工程实现角度看，本文方案具备结构清晰、资源生命周期明确、易于接入 Unity 运行时的特点，能够完成训练后高斯点云资源的加载、组织与实时显示。本文进一步给出了实验设计方案，采用帧率、CPU/GPU 帧时间、PSNR 和 SSIM 作为核心评价指标，对渲染实时性与图像保真度进行综合评估。分析表明，基于 GPU 排序与屏幕空间高斯投影的实现路径能够较好地适配实时引擎的数据流与绘制流程，具有较强的工程可落地性。最后，本文总结了当前实现的优势与不足，并讨论了 LOD、视锥裁剪、资源压缩和 SRP 深度集成等后续优化方向。

**关键词**：3D Gaussian Splatting；Unity；实时渲染；GPU 排序；点云渲染

## Abstract

With the rapid development of digital content creation, virtual reality, and interactive 3D applications, scene representation methods that balance visual fidelity and real-time performance have become a major research topic in computer graphics. Traditional mesh-based rendering pipelines are widely used in industry, yet they suffer from high modeling costs and limited adaptability when reconstructing complex real-world scenes. Neural implicit representations such as NeRF can achieve high-quality novel view synthesis, but their heavy dependence on neural inference and volume rendering makes them difficult to deploy in real-time engines. 3D Gaussian Splatting offers a new explicit scene representation that provides a practical balance between rendering quality and efficiency. Based on this background, this paper studies and implements a real-time 3D Gaussian point cloud rendering method on the Unity engine.

This work first analyzes the data representation of 3D Gaussian point clouds and the principle of screen-space splatting. The roles of Gaussian center, scale, rotation, opacity, and spherical harmonics coefficients are discussed in the rendering pipeline. A complete Unity-oriented system architecture is then designed, including data loading, parameter reordering, GPU buffer management, camera-dependent depth sorting, screen-space Gaussian rasterization, and runtime auxiliary tools. In the data stage, a binary PLY parser is implemented and spherical harmonics coefficients are reordered to match the runtime access pattern. In the rendering stage, Compute Shader is used to calculate camera-space depth keys, GPU bitonic merge sort is used to sort splats, and a custom shader approximates 2D Gaussian kernels in screen space for alpha blending. In the tooling stage, camera pose replay, benchmark measurement, and image-quality comparison are integrated to support evaluation and optimization.

From the perspective of engineering practice, the proposed method has a clear module structure, explicit resource lifecycle, and good compatibility with the Unity runtime workflow. It can complete the loading, organization, and real-time visualization of trained Gaussian point cloud assets. This paper also presents an experiment design based on FPS, CPU/GPU frame time, PSNR, and SSIM to evaluate both rendering efficiency and image fidelity. The analysis shows that the combination of GPU sorting and screen-space Gaussian projection adapts well to the real-time engine pipeline and demonstrates strong practical applicability. Finally, the paper summarizes the strengths and limitations of the current implementation and discusses future optimization directions such as LOD, frustum culling, resource compression, and deeper SRP integration.

**Key Words**: 3D Gaussian Splatting; Unity; real-time rendering; GPU sorting; point-based rendering

## 第1章 绪论

### 1.1 研究背景

三维场景的数字化表示与实时渲染是计算机图形学、虚拟现实、数字媒体技术以及游戏开发中的核心问题。传统网格模型依靠顶点、边和面描述几何结构，具备成熟的光栅化管线支持，因而长期占据主流地位。然而，当目标场景来源于现实世界采集结果而非人工建模资产时，网格重建常面临拓扑不稳定、细节恢复不足、生产流程复杂等问题。点云表示虽然绕过了拓扑构建环节，但常规点精灵或简单 splatting 方法在连续性、光照表达以及遮挡处理方面存在明显局限。

近年来，神经辐射场等隐式表示方法在新视角合成任务中取得了显著成果。该类方法通过神经网络拟合场景的体密度与辐射信息，能够呈现较为细腻的视觉效果，但其核心过程仍依赖大量采样和体积分累积，运行开销较高，难以直接用于对帧率、时延和稳定性要求较高的实时交互系统。由此可见，高质量与高效率之间的矛盾仍未被完全解决。

3D Gaussian Splatting 的提出为这一问题提供了新的解决思路。该方法以一组三维高斯分布作为显式场景基元，通过位置、尺度、旋转、透明度以及球谐颜色系数共同描述局部表面外观。与体渲染路径相比，3DGS 更便于与现有 GPU 光栅化和屏幕空间计算框架结合，在实时渲染方面具有较强潜力。基于此，围绕 3DGS 在实时引擎中的部署展开研究，既具备学术意义，也具有明确的工程价值。

### 1.2 研究现状

从三维表示方式看，当前主流方案大致可分为网格表示、体素表示、点云表示与神经隐式表示。网格方法在渲染效率、工业兼容性和编辑能力方面具有优势，但对高复杂场景的自动重建支持较弱。体素方法结构规整，便于加速结构组织，却存在存储开销较大的问题。点云方法数据采集成本较低，能够较直接地承载真实场景重建结果，但其视觉连续性长期受限于渲染模型。神经隐式表示在视觉真实感方面表现突出，却难以满足实时引擎中的大规模部署需求。

3D Gaussian Splatting 将显式表示与高质量视图合成能力进行了结合。相关研究主要聚焦于高斯参数优化、密集场景压缩、遮挡与透明混合处理、层级组织和跨平台渲染优化等方向。从工程实践角度看，已有工作多集中于研究型原型系统，针对成熟引擎环境的资源导入、运行时管理、渲染接口封装与性能评估支持仍然不足。Unity 和 Unreal Engine 虽具备强大的实时渲染生态，但 3DGS 在其内部的标准化接入仍处于探索阶段。

### 1.3 研究意义

本文研究意义主要体现在三个方面。其一，在理论层面，本文尝试将 3D 高斯表示、屏幕空间二维投影、高斯核累积与 GPU 排序机制统一到一个完整的实时渲染流程中，有助于加深对 3DGS 工程实现路径的理解。其二，在工程层面，Unity 是广泛应用于游戏开发、数字孪生、教育展示和 XR 内容制作的实时引擎平台，将 3DGS 融入该平台有助于降低新型三维场景表示技术的使用门槛。其三，在应用层面，若能够形成稳定的插件化实现，则真实场景数字化资产可更方便地进入交互式系统，为虚拟展示、沉浸式教学和轻量级可视化提供新的技术路线。

### 1.4 本文主要工作

围绕“基于 3D 高斯点云的实时渲染方法研究与实现”这一主题，本文完成的主要工作如下。

1. 分析 3DGS 的数据结构与渲染原理，明确高斯中心、旋转、缩放、透明度和球谐颜色系数在实时渲染流程中的作用。
2. 设计并实现了 Unity 环境下的高斯点云数据读取模块，支持从二进制 PLY 文件中提取顶点属性，并与运行时结构体布局建立对应关系。
3. 针对球谐系数的存储布局与 Shader 访问模式不一致的问题，设计了 CPU 端重排过程，以降低运行时重复转换开销。
4. 基于 Compute Shader 构建了相机相关深度键计算过程，并结合 GPU bitonic merge sort 实现高斯实例的透明绘制顺序排序。
5. 编写了屏幕空间高斯泼溅 Shader，实现高斯核近似、二维协方差投影、透明度累积与球谐颜色恢复。
6. 设计了若干运行时辅助工具，包括相机姿态回放、分屏比较、性能统计以及 PSNR/SSIM 图像质量评估组件。
7. 在不虚构实验结果的前提下，给出完整实验方案、评价指标与结果记录模板，为后续答辩前的真实性能采样提供基础。

## 第2章 相关理论与关键技术

### 2.1 3D Gaussian Splatting 场景表示

3D Gaussian Splatting 将场景表示为多个三维高斯基元的集合。每个高斯点携带位置向量、尺度参数、旋转参数、不透明度和颜色信息。与传统点云中“一个点仅描述一个采样位置”不同，高斯点具有局部空间扩展能力。其空间分布可用均值与协方差矩阵描述，渲染时可将三维高斯投影到屏幕空间并形成具有一定面积的二维高斯核，从而在连续性和柔和边缘表现方面优于简单点精灵。

在本文工程中，每个高斯点的数据通过 `InputSplat` 结构体进行组织，包含位置 `pos`、法向或中间向量 `nor`、一阶到三阶球谐颜色系数、透明度 `opacity`、尺度 `scale` 和旋转四元数 `rot`。这一结构既反映了 3DGS 的显式表示特点，也决定了后续 GPU 缓冲的步长与 Shader 读取布局。

### 2.2 球谐函数颜色表达

为了使场景在不同观察方向下具有较丰富的颜色变化能力，3DGS 通常采用球谐函数表示视角相关颜色。球谐函数是一组定义在单位球面上的正交基函数，低阶球谐可较紧凑地表达平滑的方向性辐射特征。本文实现中，Shader 端通过 `ShadeSH` 函数使用 0 到 3 阶球谐基对颜色进行恢复，结合当前视线方向计算最终颜色值。该方法在保留一定方向依赖性的同时，避免了高成本的神经网络推理，更适合实时渲染场景。

### 2.3 高斯协方差与屏幕空间投影

高斯点在三维空间中的形状由协方差矩阵决定。实际实现中常通过旋转矩阵与缩放矩阵构造三维协方差，再结合当前视图变换与透视投影的 Jacobian，将其近似映射到二维屏幕空间。二维协方差矩阵决定了高斯核在屏幕上的扩散范围、拉伸方向与形状特征。

本文在 HLSL 中使用 `CalcMatrixFromRotationScale` 构造旋转缩放矩阵，通过 `CalcCovariance3D` 得到三维协方差，再利用 `CalcCovariance2D` 完成屏幕空间近似投影。为了减小边界条件下的数值不稳定，还在投影后增加了最小核大小限制，以降低核半径过小导致的闪烁现象。

### 2.4 透明对象排序与 GPU 并行排序

高斯泼溅本质上属于半透明绘制问题。若渲染顺序错误，颜色累积将出现明显伪影，因此需要依据相机视角对高斯实例进行排序。CPU 排序在大规模高斯点场景中容易产生瓶颈，因而本文采用 GPU 并行排序方案。

具体而言，首先通过 Compute Shader 计算每个高斯点在当前相机坐标系下的深度，并将深度值转换为适用于基数排序或比较排序的无符号整数键；随后调用 `IslandGPUSort` 对 `(key, index)` 键值对进行 bitonic merge sort，得到适用于当前视点的实例顺序。该方法充分利用 GPU 的数据并行能力，能够较好适配逐帧更新场景。

### 2.5 Unity 渲染管线与 GPU 资源管理

Unity 提供了 Material、Compute Shader、GraphicsBuffer、CommandBuffer 等多种图形接口，使开发者能够在保留引擎运行时管理能力的同时，自定义较底层的渲染过程。本文实现采用 `GraphicsBuffer` 管理高斯数据、位置数据、排序键和排序值，并在 `OnEnable` 中统一创建资源，在 `OnDisable` 中显式释放资源，以保证 CPU 与 GPU 侧生命周期一致。相机相关绘制通过订阅 `Camera.onPreCull` 事件触发，这种设计便于在多个视角下复用同一套渲染逻辑。

## 第3章 系统设计

### 3.1 设计目标

本文系统的目标并非仅完成单次示例渲染，而是构建一套可在 Unity 中重复使用的 3DGS 运行时方案。围绕这一目标，系统设计遵循以下原则：

1. 数据表示与文件格式对应关系清晰，便于调试和扩展。
2. CPU 端仅承担必要的预处理与资源管理工作，将逐帧高开销任务转移至 GPU。
3. 渲染流程与 Unity 生命周期兼容，便于直接挂载到场景对象上运行。
4. 保留性能评估与图像质量对比能力，为后续优化和论文实验提供客观依据。

### 3.2 总体架构

系统总体上可划分为数据层、渲染层和辅助工具层三部分。

1. 数据层：负责读取 PLY 点云文件与 JSON 相机文件，解析属性信息，完成球谐系数重排和基础包围盒构建。
2. 渲染层：负责 GraphicsBuffer 创建、深度键计算、GPU 排序以及最终高斯实例绘制。
3. 工具层：负责 benchmark 统计、相机姿态回放、分屏预览以及图像质量评估。

从执行流程看，系统在启用阶段完成数据装载与 GPU 资源初始化，在每帧相机预剔除阶段执行排序与绘制，在停用阶段释放 NativeArray 和 GPU 缓冲。这一流程与 Unity 组件的生命周期紧密对应，结构简洁且便于维护。

### 3.3 数据组织设计

当前工程中，高斯点云默认从 `Assets/Resources/point_cloud/iteration_7000/point_cloud.ply` 或 `iteration_30000/point_cloud.ply` 路径读取。系统通过 `m_PointCloudFolder` 指定外层目录，运行时根据是否勾选 `m_Use30kVersion` 自动选择资源版本。该设计允许同一渲染器在不同训练迭代结果之间切换。

相机姿态信息则由 `cameras.json` 提供。系统兼容两种常见放置方式，即点云目录根路径与 `Assets` 子目录。载入后，程序会对坐标轴方向和符号进行修正，将数据集坐标系映射到 Unity 坐标系，以便后续相机回放与视角对齐。

### 3.4 渲染流程设计

渲染流程包括如下步骤：

1. 读取 PLY 文件，检查 `InputSplat` 结构体大小与文件顶点步长是否一致。
2. 在 CPU 端重排球谐系数，使同阶 RGB 系数在内存中连续，提高 Shader 访问效率。
3. 按设定采样率选取实际参与渲染的高斯数量，并构建包围盒与位置数组。
4. 将位置数组、完整高斯数据、排序距离缓冲和排序键缓冲上传至 GPU。
5. 由 `CSSetIndices` 初始化排序键，由 `CSCalcDistances` 依据当前相机视角计算深度键。
6. 调用 `IslandGPUSort` 执行 GPU 端 bitonic merge sort。
7. 通过 `Graphics.DrawProcedural` 以实例化方式绘制所有高斯点，每个实例展开为两个三角形组成的四边形。
8. 在顶点着色器中完成二维协方差估计与屏幕空间包围范围计算，在片元着色器中根据高斯指数衰减进行透明度累积。

### 3.5 辅助功能设计

为了提升系统的可验证性与可用性，本文还设计了两类辅助模块。第一类是相机控制模块 `CameraJsonRuntimeController`，其可以读取训练数据中的相机姿态序列，并通过快捷键切换视角，便于重建结果与训练视角对齐。第二类是 `GaussianBenchmarkRunner`，用于实时采集 FPS、CPU/GPU 帧时间，并通过离屏渲染结果与参考图像计算 PSNR、SSIM，从而建立一套兼顾实时性与图像质量的评价机制。

## 第4章 关键模块实现

### 4.1 PLY 点云文件解析

PLY 是点云数据中常见的文件格式。本文实现的 `PLYFileReader` 采用“先解析头部，后读取二进制顶点数据”的流程。程序逐行读取 header 信息，提取 `element vertex` 对应的顶点数量，并根据 `property` 定义累计单顶点步长，同时记录属性名称列表。头部结束后，程序依据 `vertexCount * vertexStride` 一次性申请 `NativeArray<byte>` 并读取全部顶点数据。

该实现的关键在于确保文件中各属性排列顺序与运行时结构体布局完全一致。若两者步长不一致，系统会直接抛出异常终止，以避免错误解释二进制数据导致渲染结果失真。这种“先校验、再解释”的方式有助于尽早定位数据格式问题。

### 4.2 球谐系数重排

在训练输出的 PLY 文件中，球谐系数通常按颜色通道分块存储，即先存储所有 R 通道，再存储 G、B 通道；而 Shader 恢复颜色时更适合按同阶系数的 RGB 连续布局访问。若不进行调整，Shader 端访问将变得复杂，甚至需要在运行时重复执行分量重排。

为此，本文在 `LoadPLYSplatFile` 中调用 `ReorderSHs` 完成一次 CPU 端重排。该过程以 `float*` 指针直接操作底层连续内存，对于每个高斯点将 SH 系数从通道分块布局变换为阶次交错布局。虽然这一步增加了初始化阶段的处理成本，但可以显著降低后续逐帧渲染中的访问复杂度，属于典型的“离线换在线”优化策略。

### 4.3 GPU 缓冲与包围盒构建

在成功解析点云后，系统依据 `m_ScaleDown` 参数对高斯总数进行降采样，从而在调试或性能受限场景中控制实际绘制规模。随后程序提取所有参与渲染高斯的位置，用于构建世界空间包围盒和独立的位置缓冲。包围盒一方面可作为 `DrawProcedural` 的绘制范围，另一方面也为后续引入剔除优化提供基础。

本文使用四类 `GraphicsBuffer`：

1. 高斯完整数据缓冲 `m_GpuData`，保存所有渲染所需属性。
2. 位置缓冲 `m_GpuPositions`，供 Compute Shader 快速读取位置信息。
3. 排序距离缓冲 `m_GpuSortDistances`，存放深度键。
4. 排序键缓冲 `m_GpuSortKeys`，存放实例索引。

这种分离式缓冲设计既提高了用途清晰度，也便于后续针对不同阶段实施单独优化。

### 4.4 基于 Compute Shader 的深度键生成

高斯渲染对透明顺序十分敏感，因此需要在每个相机每帧根据视角重新计算深度。本文在 `CSCalcDistances` 中读取高斯中心位置，将其通过 `_WorldToCameraMatrix` 转换到相机空间，再取深度分量生成排序键。为保证排序过程适应无符号整数比较，程序参考已有方法对浮点深度值执行位级变换，将其映射为可排序的 `uint`。

由于 bitonic merge sort 要求排序数量通常为 2 的幂，系统在初始化时将缓冲大小补齐到不小于实际高斯数量的下一幂次。对于超出真实数量的补齐元素，Compute Shader 会写入不会干扰有效数据排序结果的虚拟键值。该设计保持了排序算法结构的规整性，也避免了额外的边界分支开销。

### 4.5 GPU 并行排序实现

本文排序模块使用 `IslandGPUSort` 封装 GPU bitonic merge sort 逻辑。该实现源于 Unity HDRP/SRP 中的 GPU 排序思路，并针对当前项目做了适配，去除了与 RenderGraph 紧耦合的部分，同时保留了本地阶段和全局阶段的分步调度机制。

在实际执行中，`SortPoints` 先通过 Compute Shader 生成深度键，再创建 `CommandBuffer` 调用排序器。排序结果保存在 `_OrderBuffer` 中，供顶点着色器在实例化绘制时按排序后顺序读取真实高斯索引。相比 CPU 排序，该方案在中大规模高斯场景中更具扩展性，也更符合实时引擎逐帧更新的性能需求。

### 4.6 高斯泼溅 Shader 实现

`RenderGaussianSplats.shader` 是本文渲染实现的核心。其工作流程可概括为以下几个步骤。

1. 根据排序后实例索引读取对应高斯点数据。
2. 将位置、缩放和旋转参数转换为三维协方差描述。
3. 结合相机视角将三维协方差投影为二维协方差。
4. 计算能够覆盖二维高斯核范围的屏幕空间四边形半径。
5. 在片元阶段根据二次型指数衰减函数计算当前像素的透明度贡献。
6. 结合球谐颜色恢复结果与透明度执行混合输出。

Shader 中采用四元数与缩放构造旋转缩放矩阵，并通过 `CalcCovariance2D` 将高斯形状压缩到屏幕空间。片元阶段的 `CalcPowerFromConic` 用于计算二维高斯核指数项，对边界之外透明度极小的片元进行丢弃，从而避免无意义的像素写入。当前混合设置使用透明队列和关闭深度写入策略，适合呈现连续的高斯叠加效果。

### 4.7 运行时相机控制与评测工具

为了便于分析渲染效果，本文实现了 `CameraJsonRuntimeController` 以支持相机姿态切换。该组件能够读取训练数据相机序列并应用到 Unity 相机对象，使观察视角与原始采集视角对应。对于实验记录而言，这一能力有助于提高不同阶段结果的可比性。

`GaussianBenchmarkRunner` 则从性能与质量两个维度支持实验。性能方面，它可统计 FPS、总帧时间、CPU 帧时间和 GPU 帧时间；质量方面，它可对当前帧执行离屏截图，并与参考图像计算 PSNR 与 SSIM。由此，系统不再只停留在“能显示”的层面，而具备了量化比较的基础条件。

### 5.5 结果分析

结合当前工程实现，可以预期如下规律。

首先，随着参与渲染的高斯数量增多，深度键生成、GPU 排序和片元着色三部分的耗时都会上升。其中，排序阶段受点数量和补齐到 2 的幂次数量影响较大；绘制阶段则主要与屏幕覆盖面积和高斯核半径相关。因此，仅以点数量评估性能并不充分，还需结合实际视角下的屏幕投影密度。

其次，`m_ScaleDown` 的引入为性能与质量折中提供了直接控制手段。较大的缩减比例能够明显降低排序与绘制压力，但同时会削弱细节连续性，使高斯覆盖不足区域更容易出现空洞或边缘粗糙。若在实验中引入 PSNR 与 SSIM 指标，通常可以观察到性能提升与质量下降之间的平衡关系。

再次，球谐颜色恢复使系统在观察方向变化时仍能保持一定的视角相关外观表现，这一能力优于简单常量颜色点云渲染。不过，当前实现主要聚焦基础显示流程，对于遮挡优化、层级调度和跨管线整合尚未展开，因此在复杂大场景下仍可能面临过绘制较大、显存占用偏高和排序成本上升等问题。

### 5.6 不足分析

虽然当前实现已经打通了从数据读入到实时渲染的完整链路，但仍存在以下不足：

1. 尚未引入严格的视锥裁剪、分块剔除与层级细节调度机制，大规模场景下扩展性有限。
2. 当前透明混合和排序方案能够满足基础显示需求，但在极端遮挡和高覆盖区域下仍可能受到过绘制压力影响。
3. 渲染流程主要通过 `Camera.onPreCull` 与 `Graphics.DrawProcedural` 接入，尚未与更完整的 SRP Pass 做深度整合。
4. 目前实验记录工具已具备，但缺少本次会话内直接采集到的真实性能样本，需由后续实际运行补齐数据。

## 第6章 总结与展望

本文围绕 3D Gaussian Splatting 在 Unity 实时引擎中的应用问题，完成了一套从数据解析、缓冲组织、GPU 排序到屏幕空间高斯绘制的完整实现。研究表明，3DGS 作为显式场景表示方式，能够较自然地与实时引擎的数据流和 GPU 绘制模型结合。通过将文件解析、球谐重排和资源初始化放在加载阶段，将深度计算、实例排序和高斯绘制放在运行阶段，系统在结构上形成了较为清晰的职责划分。相机姿态控制、性能统计以及图像质量比较模块的加入，也使本文实现具备了进一步实验分析和工程迭代的条件。

从方法层面看，本文实现的主要价值在于验证了 3DGS 在 Unity 中的基础可行性，并构建了一个可持续扩展的工程骨架。该方案保留了 3DGS 在视觉质量上的优势，同时尽量借助 GPU 并行能力减轻 CPU 压力，体现了实时渲染方向中“显式表示 + 并行计算”的实现思路。

未来的改进方向主要包括以下几个方面。其一，可引入视锥裁剪、屏幕空间块级筛选和多层级 LOD，以进一步提升大规模场景下的实时性能。其二，可将当前渲染流程更深入地整合到 URP 或 HDRP 的标准渲染通道中，提高与后处理、阴影和混合管线的兼容性。其三，可探索面向移动端或 XR 设备的高斯数据压缩与渐进式加载策略，增强实际部署能力。其四，可结合更多定量实验，对不同场景、不同硬件平台下的实时性与保真度进行系统研究，从而进一步完善该方法在工程和学术层面的论证。
